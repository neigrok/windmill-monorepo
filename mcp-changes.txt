Windmill MCP — ergonomics friction log
Goal: MCP ergonomics for this product should be EXTREME. Every awkward case an
agent hits while authoring a tree over MCP goes here, so we can address it.

Format: [area] pain — what would fix it.

--- found while dumping windmill-frontend/src/skilltree/mock/roadmapTree.js into
    tree t_9362d9bc883e0a1e (a 106-node merge) ---

1. [bulk] No batch / import op. Dumping a 106-node tree took ~360 separate tool
   calls (106 create_node + ~149 connect + ~105 set_progress + kind setup). There
   is no way to hand the server a whole subgraph at once.
   FIX: an import_subgraph tool that accepts the SAME JSON shape get_tree returns
   ({title?, kinds[], nodes[{id,label,icon,color,prerequisites[]}]}, optional
   progress) and applies it in one op. This alone collapses ~360 calls into 1.

2. [create_node] Only a single `parentId`. Nodes routinely have 2-3 prerequisites
   (ceremony-director, landing-page have 3), so every multi-prereq node needs
   N-1 follow-up connect calls.
   FIX: accept `prerequisites: string[]` (or let `parentId` be an array).

3. [legend] Defining one kind takes 3 calls: add_kind (id+hue), then rename_kind
   (label), then describe_kind (description) — label/description start empty.
   FIX: add_kind should accept label + description inline.

4. [create_node] Collision semantics for an explicit `id` that already exists are
   undocumented — no stated upsert-vs-error behavior. A safe MERGE forced me to
   fetch both trees, diff ids by hand, find the collisions (radial-layout,
   email-shell), and hand-mangle the incoming ids (-fe) plus rewire every
   reference to them.
   FIX: define + return a clear "id already exists" outcome, or an explicit
   upsert flag; ideally a merge/import mode that auto-namespaces collisions.

5. [set_progress] No bulk form. Marking a fully-complete import meant 100+
   individual set_progress calls.
   FIX: bulk set_progress (accept a list of {nodeId,status}), or let the import
   in (1) carry per-node progress.

6. [create_node] Structure and progress are fully separate — create_node has no
   status/progress field — so a "dump" that includes completion state always
   needs a whole second pass. Ties into (1)/(5).

7. [merge] No diff / collision helper. To merge safely you must get_tree on both
   sides and reconcile ids yourself; the server offers no "what would collide"
   or dry-run.

8. [integrity] This tree carries orphaned data with no cleanup affordance:
   get_progress lists ids absent from get_tree (livetest-1/2/3) and
   get_diagnostics reports a dangling edge to a non-existent node 'livecheck'.
   Progress rows and edges outlive their nodes and there is no prune tool.
   FIX: a prune/gc op (or cascade on delete) + let set_progress reject unknown
   nodeIds.

9. [set_progress] The prerequisitesMet advisory is evaluated against progress at
   that exact instant, so completing a subtree in parallel (or out of dependency
   order) yields spurious prerequisitesMet:false — e.g. radial-layout-fe reported
   false because trunk-skeleton hadn't been marked complete yet in the same batch,
   though the final state is fully met. Harmless (status still records) but noisy.
   FIX: evaluate the advisory against final/committed state, or offer a bulk
   set_progress that resolves order internally.
