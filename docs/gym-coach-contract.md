# Coach conversation contract

The existing `/v1/gym/ask` JSON route accepts `{thread, question, requestId}`. `requestId` is a client-minted 8–64 character ASCII identifier containing letters, digits, `_` or `-`. Persist it with the draft before sending and reuse it, the same thread and the same question after a timeout, reconnect or retry. A different question requires a different request ID. Clients without `requestId` remain accepted; each legacy request is a new generation and cannot recover an ambiguous submission by identity.

A completed reply retains `answer`, `steps`, `read`, `proposals`, `thread` and `receipt`. It adds `generation` and `results`. `generation` contains `id`, `requestId`, `question`, `status` (`running`, `completed`, `failed`, `stopped`), `answer`, `at` (the original question acceptance time in epoch milliseconds), `steps`, optional `receipt`, and `results`. A result has `{kind:"routine-created", operationId, routineId, routineName}`. These values are server-observed durable facts, including when answer generation fails after creating a routine. Open a result using the existing routine route and handle a routine that was subsequently deleted.

The server replays the stored completed reply for the same request without another model run or charge. Reusing a request ID with a different question returns `409 ask-request-conflict`. One generation can run in each conversation. A retry while that generation is active receives `202` with its generation snapshot; a different request receives `409 ask-generation-active`. A failed generation returns `502` with `generation` and completed `results`, keeping the existing human-readable error. A retry of that request resumes the same generation and reconciles its persisted tool operations before asking the model again. `202` is pending, never a completed answer: retry the same request with backoff or read the conversation snapshot. Admission runs independently of model work, with two model slots and at most 64 queued admission requests per process. A request arriving while a different local request owns its conversation remains refused even if that generation finishes before admission reads the database. When capacity is full, new work returns `503 ask-busy`; stored completed/stopped replies and active-request snapshots remain readable through admission. If the admission queue itself is full, the refusal can precede the stored-generation read and omit a snapshot. Retry with backoff and preserve the same request ID and payload.

`GET /v1/gym/threads?limit=50&cursor=<cursor>` returns `{threads, nextCursor}`; `nextCursor` is null when no more rows remain. Pass it unchanged to fetch older conversations. Limits are 1–200. Omitting pagination parameters retains the existing `{threads}` response. The order is newest activity first, with thread ID as a stable tie breaker. Resume any row by submitting its ID to `/ask`.

`GET /v1/gym/threads/:id?limit=50&before=<cursor>` returns the existing thread object, with `turns` in chronological order for the latest page, `nextCursor` (null at the beginning), and its latest `generation`, when present. Pass the cursor as `before` to load older messages. Limits are 1–200. Messages add numeric `position` and, for durable generations, `generationId`, `requestId` and `status`. Assistant messages also carry immutable `results` using the shape above. Merge pages by position and prepend older messages. Message page sizes round up to an even count from 2–200 so each page contains complete exchanges. Omitting pagination parameters preserves the complete legacy thread read. Terminal message pairs are persisted atomically, including failed questions and partial or empty failed answers. Retry updates that same pair at the same positions. Running questions live in `generation` until terminal persistence; reconcile them by generation ID when the pair arrives. A failed answer remains marked `failed` even when its text is empty, and its request ID supports safe retry.

Thread outcomes include `created` when the conversation created a routine; `changes` then counts created routines and a sole result carries its routine identity. Full history remains stored. Model context uses the newest successfully completed exchanges, at most 24 messages and 24,000 text bytes, plus the current question and freshly read Notes/log data. Historical receipts, routine results and proposals remain available in stored history even when their text is outside model context. Coach does not claim to have consulted discarded text.

Coach can create a requested routine and save one useful new user-provided insight per generation. The server requires successful Notes and movement-catalog reads before routine creation and a Notes read before an insight save. It persists each operation with its chosen ID and complete arguments before executing it, and its observed result before model continuation. One routine creation or proposal and one note save may coexist; the operation collection also reads legacy single-operation records. Existing routine changes still use proposals and human Apply. A retry recovers those same operations and never chooses a new routine or note-save ID. Generation exclusion uses a database session lock, released on process exit; retrying the same unfinished request after restart recovers it. Deletion during an active generation returns `409 ask-generation-active`. Deleting a conversation removes its generations and messages and preserves routine, saved-note and applied-proposal consequences.

Refusals after reading a known generation retain `generation` and `results`, including later allowance or model-capacity refusals. Never discard an accepted or ambiguous request ID because a retry is refused. Deleted conversation IDs remain unavailable through an account-cascaded tombstone; delayed asks return `409 ask-thread-taken` and cannot recreate the conversation.

## Streaming and pictures (implementation contract)

Set `stream:true` on the ordinary ask body and supply a stable `requestId`. The response is `text/event-stream`, with `Cache-Control:no-cache` and proxy buffering disabled. Every visible event is named `snapshot`, carries `id: <generation-id>:<revision>`, and has JSON `{thread,generation}`. `generation` uses the fields above and adds monotonic numeric `revision`; `answer` is the complete current visible answer text. Replace that generation's text on each snapshot; never append the entire snapshot. Internal thinking and tool arguments are never sent. A reconnect repeats the same POST and begins with the authoritative snapshot, so clients need not retain every event. Ignore revisions already rendered. A terminal `completed`, `failed` or `stopped` snapshot closes the stream. Refusals before a generation exists use an SSE `error` event containing the ordinary `{error,status,code?}` body and close. Heartbeat comments keep idle connections open.

`POST /v1/gym/threads/{thread}/generations/{requestId}/stop` has an empty body. It requests cancellation and returns `{thread,generation}`. A running reply may include `stopRequested:true`; cancellation becomes final at `status:"stopped"`. Stop preserves partial text and completed routine/proposal/note actions. After a process restart, Stop reconciles already committed actions without executing an uncommitted pending write. A stopped request replays its terminal snapshot and does not restart; continuing is a new message/request ID. A failed request may retry the same ID. Disconnecting the client leaves the server generation running so reconnect can recover it. Stop is owner-scoped and idempotent; a missing/foreign request returns 404.

Upload one picture with `PUT /v1/gym/threads/{thread}/attachments/{attachmentId}`. The body is the original image bytes, with `Content-Type:image/jpeg` or `image/png`; IDs follow the same 8–64 character rule. Limits: 5 MiB encoded, 4096 pixels per edge, 16,777,216 decoded pixels. JPEG and PNG are decoded and validated (including PNG chunk CRCs); filenames/extensions are not trusted. Clients should convert unsupported picker formats to JPEG/PNG and retain the draft on upload failure. The response is `{attachment:{id,mediaType,width,height,bytes}}`. Repeating the same ID and same bytes replays the metadata; a changed payload with that ID returns 409. Upload alone creates no conversation or title. At most 30 new images may be uploaded per account in a trailing 24-hour window (`429 ask-image-limit`); identical replays do not count again. Two upload workers and a four-request in-flight bound protect request loops; a temporarily full queue returns `429 ask-image-busy`.

Add `attachmentIds:[attachmentId]` to the ask body (maximum one). The question may be empty when a picture is present. The first title is the question verbatim, or `Photo` for an image-only question. The generation and its user message carry `attachments:[{id,mediaType,width,height,bytes}]`; text and image references together are the request's immutable retry payload. The full image bytes are stored once privately, never duplicated as base64 in conversation history. `GET /v1/gym/threads/{thread}/attachments/{attachmentId}` returns the original validated bytes with a private/no-store cache policy, and returns 404 for absent/foreign images. Linked images live with their conversation and cascade on conversation/account deletion. Abandoned unlinked uploads expire after 24 hours; cleanup on subsequent uploads never removes an image linked to retained history. Model context includes at most the three newest pictures within its text context, including the current picture.

## Provider transport and usage

Coach uses incremental Anthropic Messages responses for both streaming and buffered clients. The server-owned `COACH_ANTHROPIC_BASE_URL` defaults to `https://api.anthropic.com`; tests may set a loopback HTTP endpoint implementing the same protocol. It never selects a canned Coach response path. Visible text from tool rounds remains in the ordered answer; thinking and signatures stay internal.

The usage ledger preserves every input, cache and output token count reported by the vendor. Interrupted streams may end before the final cumulative output count arrives, so those observed counts can be incomplete; they are not represented as exact final billing. A stream that reached `message_start` counts as a model turn and does not refund the daily question ration.

## Coach Notes saves

`save_note` is a `gym:write` tool accepting `{id,title,body}`. It appends a useful NEW insight actually supplied by the user, using their own wording for constraints, at bottom precedence. It never edits, deletes or reorders an existing note. Coach must first read Notes and avoid repeating existing information. Bounds match Notes: ten per account, 1–60 Unicode code points in the trimmed title, at most 500 UTF-8 bytes in the trimmed body. Exact title/body duplicates reuse the existing note without moving or redating it, including at capacity.

Coach assigns `note_<generation-id>` and an independent `op_note_<generation-id>` operation identity. The tool returns `{saved:true,note:{id,position,title,body,updatedAt}}` only after a durable save. The receipt in `gym_note_saves` is owner-scoped and written atomically with the note insert or exact-text deduplication. Reusing an ID with different text is refused. Original receipts survive user edits/deletion so a lost-ack retry cannot overwrite or resurrect a note. They cascade on account deletion. A successful replay proves the original save, not the note's current presence; the model receives that distinction on recovery. No new conversation `results` kind is introduced: generic tool steps and the durable operation receipt record the save.

The owner-provided main/style/workflow/boundaries prompt is stored verbatim in `AnthropicAsk.cpp`. Factual tool, privacy and context rules are separate. They require equipment/variant clarity and honest movement-pattern coverage, and keep internal IDs and tool narration out of replies unless useful to the user. The runtime still fetches current sessions and Notes before making a model request.
