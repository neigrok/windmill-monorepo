# Lift — feature dossier

**Lift** is a shipped, standalone iOS training log with an LLM coach: SwiftUI + SwiftData, ~8.7k
lines of Swift across 35 commits and six working days (2026-03-07 → 2026-04-11), with ~57 tests in
1,042 lines — one of which has been red for the last ten commits without anyone noticing. It has
templates, a live set logger, session history, progress charts, a five-tool AI coach with a
propose→approve→apply gate, an interactive Live Activity, and a complete StoreKit subscription funnel
in front of a tier that throws "coming soon" on every message.

This document is the code-verified inventory behind the gym section of `docs/PRODUCT_LOG.md`. It
exists because **Lift is not a codebase we migrate — it is a spec written in Swift and a bug
ledger.** Its craft (the range-adaptive weight ladder, the human approval gate, write-through
persistence) is worth stealing precisely; its four structural stops (free-text exercise identity, a
plan that is the same object as the log, no prefill from last week, a paid tier that never existed)
are worth never repeating. Every feature below was read out of the source, not inferred from file
names — **211 capabilities** across sections 1–10, with what Lift *doesn't* do in section 11.

## How to read this

**maturity** — `shipped` · `partial` · `stub` · `spec-only` (appears in `docs/specs/` or
`docs/tasks/` and nowhere in the app) · `dead code` (written, zero call sites).

**cost** — what it would take to stand this up in a web + shared-C++-backend product: `free` (the
Windmill platform already does it) · `port` (the logic transfers, rewrite the shell) · `rebuild`
(net-new against a server) · `drop` (no analogue, or superseded by the platform).

There is deliberately **no verdict column**. What gym builds is decided in `docs/PRODUCT_LOG.md`
under "Gym — the third product", not by a checkbox beside 266 features. Citations are
`lift:Path/To/File.swift:LINE`, relative to the Lift repository.

## 1. Live workout — the core loop

The logging surface is Lift's whole product thesis in one screen: **one exercise, one weight, one rep count, one button.** Every competitor shows a grid; Lift shows a single value at a time and spends its cleverness making that value need as few taps as possible — which is also the only reason a full set can be logged from a locked phone. State lives in one `@MainActor @Observable ActiveWorkoutManager` (365 lines) holding the session, a per-exercise defaults dictionary **keyed by exercise name**, a cursor of (exercise index, set number), and the in-flight weight and reps. Every set is written to SwiftData the instant Save Set is tapped — no draft, no commit phase, no undo. The taste is opinionated and mostly right: increments auto-scale with load, negative weight is legal, extra sets past target are always allowed, and nothing ever auto-advances. What is absent is everything a per-set state machine would give you: no RPE, no notes, no set kinds, no rest target, no way to fix a set without leaving the screen, no lbs, and — the structural one — **no prefill from last week**, only from the template's static `startWeight` or from earlier sets in the same session.

**Sharp edges**

- Exercise identity is a **free-text String** everywhere. The defaults dict is built with `uniquingKeysWith: { _, last in last }`, so the same movement twice in one template — bench heavy then bench back-off, a legitimate program — collapses into one entry sharing one set counter (`lift:Lift/Services/ActiveWorkoutManager.swift:114-117`). Renaming an exercise mid-workout orphans every set already logged under the old name.
- The paging is theatre: `exercisePage(for: index)` ignores its `index` and renders the same live manager state on every page, and the header sits outside the `TabView` — so mid-swipe both pages show identical numbers (`lift:Lift/Views/Workout/ActiveWorkoutView.swift:85-113`).
- Negative weight quietly poisons the headline metric: an assisted set contributes **negative volume** to `totalVolume` and to every chart. The feature shipped; the metric was never revisited.
- The weight ladder is copy-pasted into the widget target (`lift:LiftLiveActivity/LiftLiveActivityWidget.swift:252-272`) because `Formatters` is not a member of that target — two sources of truth for the product's most distinctive rule.
- `Formatters.duration` has no hour rollover: a 95-minute session reads "95:12", and the test asserts `duration(3600) == "60:00"`.
- The toolbar Finish has no confirmation even with zero sets logged — an accidental tap writes an empty finished session into history and the charts.
- Discard is fully implemented and tested but **unreachable** from the live screen; its only caller is the launch-time recovery alert, and the back button is hidden.
- The pyramid capsule is drawn at `.opacity(0/1)` rather than conditionally inserted, so the header doesn't jump when swiping between pyramid and non-pyramid exercises (`eadb220`) — but it hardcodes `Int(weight)`, so a 72.5 kg target displays as "72 kg".
- Invalid weight input fails silently, keeping the old value with no feedback. There is no tap-to-type for reps at all: a target of 10 to an AMRAP of 25 costs fifteen taps.
- The rest timer does not reset when you switch exercises, and resume restamps `setStartDate = .now` regardless of how long the session sat.
- `nextExercise()` and `StopwatchService.restart()` are tested and/or written but have zero UI callers.

## 2. Templates & the exercise library

The planning surface is deliberately anemic and it is the right instinct pushed one step too far. A `WorkoutTemplate` is a name, an ordered list of exercises, and a created date — no description, tags, schedule, folder, or archive. There is no program, mesocycle, or week: **a template is one training day**, and a user's split is N templates in a flat list. Each exercise carries sets × reps @ weight, optional per-set pyramid targets, and muscle-group tags. There is **no exercise catalog** — every movement is retyped free text, so "Bench Press" and "Bench press" are two different lifts forever, and that single decision is the root of most of the sharp edges in this dossier. The editor stages its edits and can be cancelled; the preview screen writes the identical gesture straight through to the database. And the template is the **only** entry path into a workout: there is no ad-hoc session, so adding face pulls once means permanently rewriting your program.

**Sharp edges**

- **No exercise catalog.** Every movement is retyped free text, with no search, no aliases, and no stable id. This is the single decision the rest of the dossier keeps paying for.
- `updateTemplate` deletes every `ExerciseTemplate` row and recreates it on every save, so UUIDs churn each edit and per-exercise identity is fiction — a real hazard for any backend that has to replicate an edit or reconcile a concurrent one. `lift:Lift/Repositories/SwiftDataTemplateRepository.swift:38-45`
- The muscle taxonomy is **lopsided**: chest, back, shoulders, biceps, triceps, **legs**, core, glutes, forearms, calves (`lift:Lift/Shared/MuscleGroup.swift:4`) — one `legs` bucket against three separate arm buckets, so quads versus hamstrings cannot be expressed. Attribution is also read live from templates, so deleting a program erases muscle tags from past history.
- Two mutation models for the identical gesture: staged and cancellable in the editor, immediate and unconfirmable in the preview. The preview path is also the **only** one that preserves an exercise's UUID; every other edit destroys and recreates the rows.
- Full-swipe delete of an entire program with no confirmation and no undo. The row also reads "1 exercises".
- Sorting is `createdAt`-desc only — no manual order, no favourites, no last-performed — so the template you run most sinks as you add others.
- Reordering relies on an undiscoverable long-press drag: there is no EditButton and no visible handle. `ExerciseEditorRow` takes a `@Binding` it never mutates.
- `ExerciseRowView` and the editor's private `ExerciseEditorRow` are near-identical duplicates that have already drifted — one uses `Formatters.weight()`, the other raw `Int(weight)`.
- Defaults (3×10 @ 20 kg) are hardcoded in three places: the model init, `ExerciseEditorState`, and the coach's JSON parse. The 10 muscle-group names are hardcoded in a fourth.
- The coach's `createTemplate` applies **no clamping at all** to values the UI constrains to 1…20 / 1…100 / 0…500, and negatives pass. `addExercise` has no `muscleGroups` field, so every AI-added exercise is untagged and invisible to the muscle chart.
- The pyramid ladder is an opaque JSON blob, so the database can never query or aggregate it — fine on-device, a real constraint for a server that wants planned-versus-actual.
- Not one test covers the editor, the repository against a real store, or the list.

## 3. AI coach

The coach is Lift's differentiator and its cautionary tale. The architecture is genuinely good: one 90-line `LLMBackend` protocol, a provider-neutral tool-schema type tree serialized once in Swift, five tools, and — the best idea in the repo — a **blocking human gate**. When the model proposes a change to a program, the agent turn suspends on a `CheckedContinuation` until the user taps Apply or Reject, and the decision is fed back as literal text ("User APPROVED the proposed changes"). The model can read everything and write nothing. Four backends exist because the design spanned a ~4k-token on-device window (Apple Intelligence) and a 200k hosted one (Claude, `max_tokens` 4096, raised from 1024 in `b57e5cd` after replies were being truncated) — an asymmetry that is the entire justification for the abstraction. And the tier the app actually sells does not exist: `PaidLLMBackend.send` unconditionally throws "coming soon" while `isAvailable` returns `true`, so a paying subscriber is auto-adopted onto a backend that errors on every message instead of being shown the lock.

## 5. History & crash recovery

History is a deliberately thin reverse-chronological list of finished sessions, with one drill-down that doubles as a light editor and as the jump-off point into per-exercise charts — no search, no filter, no calendar/date-range picker anywhere in the UI, though a capable paginated query exists and is wired exclusively into the AI coach's tool layer. Crash recovery rests on a single rule — a session with `finishedAt == nil` is by definition abandoned — with no time heuristic, no auto-finish, and no "decide later" escape; a session from three weeks ago is offered for resume in identical words to one from two minutes ago. Durability is achieved by brute force: every saved set writes straight through to SwiftData, so a kill loses at most the one unsaved set in flight. The persistence layer's failure mode is equally blunt: a corrupt store is deleted and rebuilt with no backup, no export, and no confirmation.

## 7. Shell, persistence, settings, money

- StoreKit subscription group id in code is `B44D3AC3` (`lift:Lift/Shared/AppConstants.swift:12`, matching `Configuration.storekit`), while `lift:docs/specs/settings-subscription.md:95` says "21575289" — a spec/code divergence, and neither was ever exercised locally since `Configuration.storekit` isn't wired into the Xcode scheme.
- The App Group divergence: `AppConstants.appGroupIdentifier = "group.com.lift"` (`lift:Lift/Shared/AppConstants.swift:7`) is not the group named in the entitlements file, `group.com.tobeaanounced.Lift` (`lift:Lift/Lift.entitlements:7`) — the identifier named in code is not the one actually entitled, so the shared App Group container is dead on arrival.
- The boot path destroys user data to stay alive: any `ModelContainer` open failure deletes the store and retries silently, and the migration plan's `stages` array is empty, so the first breaking schema change ships as total, uncommunicated data loss.
- Settings' budget is almost entirely LLM provider plumbing (four-way picker, model pickers, two sets of Keychain-backed key fields) and has zero of the two things a lifting app is expected to have: a units setting (kg hardcoded in ~66 sites) and any data control (no export, import, delete-my-data, or backup).
- Exercises are identified by free-text name everywhere in the schema and every repository method — no catalog, no ids, no aliasing — so a template edit's delete-and-recreate pattern and any exercise rename both silently fork or orphan history.
## 8. Written intent — the specs and the filed backlog

`docs/specs/` is eight documents, one per feature area, written in a single register: data-model tables, numbered lifecycle pipelines, exact pt/opacity/font values, and an "Outcomes" acceptance table closing every doc — roughly 110 stated acceptance rows across the corpus. They read as reverse-documentation, not a forward plan: they name real Swift types (`ActiveWorkoutManager`, `SessionRecoveryService`) and describe behavior the code already had. `docs/tasks/` is run as the literal issue tracker — per `.claude/CLAUDE.md:4-7`, a task file is deleted the moment its work lands, so the eight files still on disk are not a wishlist skimmed off the top; they are everything the authors knew was unfinished at the moment they stopped writing. ## 9. Evolution — the build arc

Lift (born "Dimly") is 35 commits across six working days: 2026-03-07, 03-08, 03-14, 03-15, 03-31, and 04-11 — a five-week span with all the actual writing compressed into six sittings. The arc is unusually legible because each day has one job. Day one (`dcada15`) is a bare Xcode template. Day two (`0b95afc`, "Initial commit: Dimly workout tracking app") lands the entire tracker — templates, active-workout logging, history, progress analytics, and a Live Activity with Dynamic Island controls — in one 3,015-line commit, whole, with no incremental build-up visible in the history. Day three is architecture first, features second: `4d41e6d` extracts repository protocols and constructor injection and deletes the pre-refactor `WorkoutService`, creating the seams every later test depends on; the AI coach then lands the same day in `34f5f19`, one 3,848-line commit shipping the LLM backend protocol, the tool-use loop, streaming, conversation history, and the proposal/diff approval flow together with the first eight test files. Day four (03-15, 14 commits) is the one-day monetization sprint: StoreKit 2 subscription and paywall, a second and third LLM provider (Apple Intelligence, then OpenAI), a redesigned provider picker, instant-apply settings with theming, the Dimly→Lift rename across 93 files, and a production-hardening pass (crash recovery, Keychain scoping, schema versioning). The last two days are pure bug-fix and polish, and are treated in full in Section 10.

Three things were rewritten outright rather than extended. The progress charts were built interactive on 03-31 (`33e5915`) and then substantially rewritten on 04-11 (`725533b`, 261 insertions / 181 deletions across 4 files) once the interactive version proved to have a gesture conflict, a per-render recompute cost, and two analytics bugs — the rewrite is a correctness pass layered on top of the earlier interactivity pass, not a reversal of it. Chat history was reworked from one growing JSON blob to one-file-per-conversation-plus-index after it started OOM-crashing on launch (`821221f`), with a one-shot migration bolted on and never tested. The provider/backend surface expanded three times in one day (Apple Intelligence and OpenAI added, then the picker redesigned twice more in `6e33906` and `52212b2`) and produced three separate fix commits for state it couldn't keep straight — selected provider, usable provider, and active backend were three different things that kept getting collapsed into one.

The specs in `docs/specs/` were written against this already-built codebase — they name the real types, not proposed ones, and every one closes with an Outcomes table that reads like generated acceptance tests for behavior that already existed. Four historical items are visible only in git, not in any surviving file: the pre-refactor `WorkoutService`; a pushed `LLMSettingsView` sub-screen (added `1be82a8`, collapsed into one inline settings screen 254 lines later in `d74ce93`); the settings "Done" button (removed `b018529` for instant-apply); and three phase-spec docs (test infrastructure, the 700-line LLM-coach design doc, post-workout share) deleted once each was implemented, per the project's own doc-lifecycle rule.

## 11. What Lift does not do

**Logging.** No RPE, RIR, tempo, or per-set notes. No set type — no warmup, drop set, failure set, or AMRAP marking. No supersets, circuits, or exercise grouping within a session; exercises are a flat ordered list, and the same exercise cannot appear twice in one template (its defaults collapse to one entry, keyed by name). No non-barbell exercise types — every exercise is (weight × reps), so cardio, planks, holds, and bodyweight work have no honest representation. No plate calculator, no bar-weight awareness, no configurable weight increments beyond the fixed stepper table. No rest-timer target, countdown, alert, sound, or notification, and no per-exercise or global default rest time — the only timer counts up from the last saved set. No units system: kg is hardcoded into every formatter, the 0–500 weight range, and the step tables; there is no lb path anywhere in app, tests, or specs.

**Programming.** No exercise catalog or search — exercise identity is a free-text string name everywhere (sets, history, analytics, the coach's `fetchExerciseDetail`), so a typo silently forks an exercise's history and a rename orphans it. No ad-hoc/blank workout: every session starts from a template, and no exercise can be added to an in-progress or past session without editing the template itself, which changes it permanently — there is no session-scoped override. No template duplication, folders, favorites, or archive; the template list is flat. No scheduling or periodization — templates carry no assigned day, and there's no notion of a training week or program cycle.

**Analysis.** No PR detection or celebration anywhere — the post-workout sheet is three descriptive stats with no comparison to history. No estimated-1RM in the UI, despite the Epley formula being computed for the coach's tool output. No streaks, calendar/heatmap view, or weekly volume targets. No date-range filter on any chart, no search or filter in history, no month/week grouping — history is one flat reverse-chronological scroll. Muscle-group volume double-counts across every tagged group on a multi-tag exercise rather than splitting it, and is computed all-time with no window.

**Data & trust.** No accounts, cloud sync, multi-device support, backup, or export/import in any format. All state is device-local across SwiftData, Keychain, and the filesystem. The one built recovery path for a corrupted database deletes the entire local store and shows "please reinstall." No bodyweight, body measurements, or progress photos — the only tracked quantity is barbell load. No HealthKit or Apple Watch integration, no heart-rate/calorie export to the Fitness app. No structured error type anywhere — failures are ad hoc per view, untyped strings matched by `.contains("Error")`, or silent. No undo on any destructive action (discard, swipe-delete, Clear All chat history) and, in the specs, no confirmation step before any of them. No onboarding, sample templates, or actionable empty states (filed, never built) — a new user faces an empty list and must author a template from nothing.

**Coach.** No social layer — no sharing a session, no friends, no leaderboards, no human coach. No free-tier allowance for the AI coach beyond the on-device Apple Intelligence path — it is fully locked or fully open, no trial, no message quota. No memory beyond the last 50 messages of the current conversation plus one free-text personalization field; the coach re-derives all context from tools every conversation, with no summarization of what's trimmed. No offline behavior specified for the coach. The paid "Lift Intelligence" tier is purchasable through a complete StoreKit 2 flow and non-functional behind it — `PaidLLMBackend.send()` unconditionally throws "coming soon."
